# E2V Training Configuration and Implementation Guide

## Overview

This document outlines the updated JSON configuration structure for Elements-to-Video (E2V) training, explains each section's purpose, details the implementation approach, and identifies files that need updating.

## Section Descriptions

### elements
Defines the reference elements to use for conditioning:
- **name**: Identifier for the element type
- **suffixes**: File suffixes to match for this element
- **required**: Whether this element is required for training
- **processors**: Which processors to apply to this element and their specific configurations

### processors
Global configuration for each processor type:
- **resolution**: Target resolution for processing
- **preprocessor**: The preprocessing method to use (resize, center_crop, letterbox, etc.)
- **batch_size**: Maximum number of elements to process in a single batch
- **processor-specific settings**: Additional settings for each processor type

### tensor_combinations
Defines how processor outputs combine into final tensors:
- Each key is the name of an output tensor
- Each value is a list of processor types whose outputs should be combined
- Common combinations:
  - **reference_latents**: VAE-encoded reference images
  - **mask_latents**: Binary masks for conditioning
  - **combined_condition_latents**: Combined conditioning for the model
  - **reference_embeddings**: CLIP embeddings for semantic conditioning

### visualization
Optional debugging visualization settings:
- **enabled**: Whether to generate visualizations
- **output_dir**: Where to save visualizations
- **frequency**: How often to generate visualizations
- **processors**: What to visualize and how

## Implementation Design

### Processor Architecture
Each processor will have a two-phase architecture:
1. **Preprocessing Phase**: Transforms input tensors to the right format
2. **Encoding Phase**: Applies model-specific encoding when models are available

This separation allows for:
- Efficient batch processing (process multiple elements at once)
- Keeping models loaded on GPU throughout processing
- Clear separation of concerns between different processing steps

### Batch Processing Approach
To maximize GPU efficiency and avoid loading/unloading models:
- Group elements by processor type
- Process each group in batches according to batch_size configuration
- Keep models loaded on GPU for the duration of processing

```python
# Group elements by processor for batch processing
processor_inputs = {proc_name: [] for proc_name in self.processors}
processor_configs = {proc_name: [] for proc_name in self.processors}
processor_elements = {proc_name: [] for proc_name in self.processors}

# Map elements to processors
for element_name, element_info in element_data.items():
    element_image = element_info["image"]
    element_config = element_info["config"]
    
    # Check which processors are configured for this element
    for proc_name in self.processors:
        if proc_name in element_config.get("processors", {}):
            processor_inputs[proc_name].append(element_image)
            processor_configs[proc_name].append(element_config)
            processor_elements[proc_name].append(element_name)

# Process each processor type in batches
for proc_name, processor in self.processors.items():
    if not processor_inputs[proc_name]:
        continue
        
    # Get the appropriate model for this processor
    model = self.models.get(proc_name)
    
    # Batch process all elements for this processor
    batch_results = processor.batch_process(model, processor_inputs[proc_name], processor_configs[proc_name])
```

### Tensor Combination Logic
The `_combine_pathways` method will implement the tensor combination logic based on the configuration:

```python
def _combine_pathways(self, data, processed_data):
    """Combine results according to tensor_combinations configuration."""
    result_data = dict(data)
    
    # Get tensor combination configuration
    tensor_combinations = self.config.get("tensor_combinations", {})
    
    # Process each defined output combination
    for output_name, processor_list in tensor_combinations.items():
        components = []
        
        # Collect tensors from each processor
        for proc_name in processor_list:
            if proc_name not in processed_data or not processed_data[proc_name]:
                continue
                
            # Get all results for this processor
            proc_results = list(processed_data[proc_name].values())
            
            # Sort by position
            proc_results.sort(key=lambda x: x.get("position", 0))
            
            # Extract tensors based on processor type
            if proc_name == "vae":
                tensors = [r.get("latents") for r in proc_results if r.get("latents") is not None]
            elif proc_name == "clip":
                tensors = [r.get("features") for r in proc_results if r.get("features") is not None]
            else:
                tensors = []
            
            components.extend(tensors)
        
        # Skip if no components
        if not components:
            continue
            
        # Determine combine method based on output name
        if "latents" in output_name:
            # Concatenate along channel dimension (dim=1) for latents
            result_data[output_name] = torch.cat(components, dim=1)
        elif "embeddings" in output_name:
            # Concatenate along sequence dimension (dim=1) for embeddings
            result_data[output_name] = torch.cat(components, dim=1)
    
    return result_data
```

## Processor Implementations

### 1. BasePathwayProcessor
- Initialization with config and output_names
- Generic batch processing interface
- Consistent method signatures
- Fallback to individual processing when batching isn't possible

### 2. VAEPathwayProcessor
- Uses letterbox preprocessing to maintain aspect ratio
- Handles frame repetition for reference images
- Applies VAE encoding when available
- Specialized batch processing for VAE tensors
- Supports element-specific configuration via `element_config["processors"]["vae"]`
- Automatic tensor stacking for compatible shapes

### 3. CLIPPathwayProcessor
- Uses center_crop preprocessing as expected by CLIP
- Applies CLIP encoding when available
- Extracts appropriate features from CLIP output
- Supports batch processing for CLIP vision models
- Supports element-specific configuration via `element_config["processors"]["clip"]`
- Handles disabled CLIP pathways gracefully

## Implementation Guidelines

1. **Processor Interface**:
   - BasePathwayProcessor provides common interface
   - Two-phase design: preprocessing + encoding
   - Forward method that takes models, tensors, and element_config
   - Batch processing for multiple elements
   - Return dictionary with tensors and metadata following framework convention

2. **Data Flow**:
   - Dataset loads elements and groups them by processor type
   - Elements with the same processor are processed in batches
   - Models are kept on GPU throughout processing
   - Tensor stacking for efficient batch encoding
   - Combined results assembled according to tensor_combinations
   - Trainer receives properly named tensors ready for training

3. **Preprocessing Implementation**:
   - VAEPathwayProcessor: Uses letterbox preprocessing (maintain aspect ratio with padding)
   - CLIPPathwayProcessor: Uses center_crop preprocessing (crop to square aspect ratio)
   - All preprocessing uses finetrainers.functional (FF) utilities

4. **Framework Consistency**:
   - Follow existing processor patterns (return dictionaries with output_names as keys)
   - Use functional utilities from finetrainers.functional for preprocessing
   - Maintain consistent naming conventions (_latents, _embeddings)
   - Keep the dataset wrapper as the orchestrator

5. **Error Handling**:
   - Clear messages when required elements are missing
   - Proper validation of configuration
   - Graceful handling of missing processors

This configuration and implementation approach provides a flexible, efficient foundation for E2V training while maintaining compatibility with the framework patterns.
